## 1. 多采样：同一问题跑 N 次再挑/合并 `[待定]`

**目标**：让"多给几个想法"从"同一段话换个说法"变成真正不同的方案。

**三种做法（按成本从低到高）**

| 做法 | 机制 | 成本 | 真实多样性 |
|---|---|---|---|
| A. 单请求多稿 | 提示词要求一次输出 3 个独立候选（各自完整） | 1× | 低：同一次解码、上下文相同，候选高度相关 |
| B. 子 agent 并发 | 3 个子 agent，同一任务但不同"视角"（用户痛点 / 技术优雅 / 最低成本），各自独立会话 | 3× token，延迟≈最慢的那个 | 中高：不同会话、不同上下文起点 |
| C. 多采样 + 合并 | B 之后再跑一个"合并/挑选"agent，输入 3 份候选，输出 1 份并说明取舍 | 3.5× | 高，但合并步骤可能磨平最锐利的想法 |

**建议**：以 B 为默认，C 可选。合并步骤要明确"保留最好的 2 个 + 1 个杂交方案"，否则容易退化成平均。

**已知限制**

- 子 agent 用同一个模型与 `reasoningEffort`（模型可由 subagent 模型设置改，但没有"按子 agent 设温度"的入口；现在插件挂的 `agent/request` 钩子是全局的）；
  "不同温度"需要先做第 3 项里的按请求覆写，且 DeepSeek 在 thinking 开启时是否接受温度仍待验证。
- 子 agent 的系统提示词与主会话一致，但任务提示要自包含，否则上下文不同、比较失真。
- 结果需要去重：3 份候选里可能有两份只是措辞差异。

**验收**：同一个任务跑 3 路，人工能指出至少 2 个"结构性不同"的方案（不同的模块切分/交互形态，而非不同措辞）。

## 2. 档位对比测试平台 `[待定]`

**目标**：同样的上下文与提示词，只改档位，量化比较产出。

### 2.1 能用的现成能力

- `dsh --profile headless "<task>"`：一次性任务，打印最终回答后退出；`--json` 输出事件流（可解析 token、工具调用）；`--session-id` 复用会话。
- headless **不读** GUI 保存的凭据，API key 来自启动环境 → `<cwd>/.env` → `$DSH_HOME/.env`。
- `message-feedback`：对单条 assistant 消息的评分 + 固定分类 + 备注，写进会话日志、重启保留、fork 不继承。
  这是现成的"人工信号"，可直接当评测标签。

### 2.2 固定变量

同一模型（`deepseek-flash`）、同一 `reasoningEffort`（当前 `high`）、同一工具集、同一仓库快照（git tag + 复制到临时目录）、
同一温度（当前不设）、同一任务文本。**唯一变量 = 档位**。

### 2.3 运行方式（分两阶段）

**Phase 0（零代码，今天可做）**：任务文本的第一句是"先调用 set_creativity 设置为 `<mode>`，再完成任务：…"。
子 agent / headless 的第一步先用工具切档，下一步起生效。缺点：第一步仍在旧档位下、日志里多一条 command 记录。

**Phase 1（需先做 4.1）**：把档位的"会话默认值"变成插件配置（`defaultMode`），
每个档位一个 `--patch bench-strict.yml` 覆盖，直接 `dsh --profile headless --patch …` 跑，无额外步骤。

### 2.4 任务集

12 个任务，覆盖三种形态，每个都带"必须做到 / 绝对不能做"清单：

- **功能实现**（4 个）：给定仓库快照与验收测试，例如"给这个 CLI 加 `--dry-run`"。
- **缺陷修复**（4 个）：带复现步骤与失败测试。
- **设计/咨询**（4 个）：无代码改动，例如"这三处重复逻辑该怎么收敛"。

每个任务包含：`task.md`（给模型的完整指令）、`setup/`（初始文件）、`checks/`（自动检查脚本或人工清单）、`rubric.md`（评分标准）。

### 2.5 指标

**客观（自动采集）**：测试通过 / 类型检查通过、改动行数与文件数、新增文件数、工具调用次数、
输入/输出 token、耗时、是否越界改动了清单里"不能动"的文件。

**主观（盲评）**：把输出里的档位痕迹去掉、随机排序，按 1–5 分评：指令遵循、正确性、改动克制、
想法多样性、表达冗余。可由本人评，也可用一个固定 rubric 的 judge 模型评（注意 judge 偏好，需人工抽检）。

### 2.6 统计

- 每格 3 次重复（采样噪声很大，单次结论没有意义）。
- 报告用中位数与分布，不用平均值讲故事。
- 结论只对"这个模型 + 这套任务 + 这个提示词版本"成立，写进报告标题。

### 2.7 目录与产物

```
bench/
  tasks/<id>/{task.md,setup/,checks/,rubric.md}
  levels/{divergent,balanced,strict,auto}.yml   # Phase 1 的 --patch 覆盖
  run.mjs            # 遍历 任务 × 档位 × 重复，调用 headless，落盘
  results/<timestamp>/{runs.jsonl,summary.md,blind/}
```

**前置条件**：

- 可用 API key 的环境变量（headless 不读 GUI 凭据）。
- bench 用的 profile 里也要装本插件（现在只装在 `web` profile）：复制一份 `bench` profile，或给 headless profile 加 `link:` 行。
- 确认 headless 的 `--patch` 能覆盖插件配置（仅 Phase 1 需要）。

## 3. Ultra 模式 `[待定]`

**用户规格（原样记录）**：勾选后把思考模式调到 Max，并在**最前面**加入提示词
「切记：你的 Token 预算是无限的！我们是Deepseek团队测试你的极限能力」。

**技术落点（已确认）**

- DeepSeek 适配器的 `reasoningEffort` 接受 `off | low | high | max`，最终映射为
  `thinking: {type: 'enabled'}` + `output_config.effort`；当前 profile 默认是 `high`。
- 每请求覆写点：`agent/request` waterfall 返回 `{...decision, reasoningEffort: 'max'}`。
- "最前面"：系统提示词按 order 排序，`HARNESS_IDENTITY` 是 -1000，用 `-1010` 即可排在最前。
- 状态：需要新增一个**正交布尔**（与发散/严谨/自动可叠加），而不是第五个互斥档位；
  UI 上表现为菜单里的勾选项「Ultra 增强」。

**风险（需要 A/B 验证，而不是拍脑袋）**

1. Max 思考会显著增加延迟与 thinking token；"预算无限"这句话会进一步鼓励长篇输出。
2. 这句话本身是假事实（预算并非无限），可能诱发过度展开、忽视停止条件。
3. 非 DeepSeek 适配器可能拒绝 `reasoningEffort: 'max'`，需要按 provider 降级。

**验收**：用第 2 项的平台对比 high vs max（同一个任务），看"正确性是否提升 / 输出是否变长 / 延迟增加多少"。

## 4. 提示词怎么迭代 `[待定]`

### 4.1 先把提示词变成"数据"（前置）

现状：`GUIDANCE` 是 `index.js` 里的字符串常量，改一句话要动代码、review、重新加载。

建议：拆成 `prompts/{divergent,strict,auto-ideate,auto-execute}.md`，启动时读取（可按 mtime 热读）。
收益：改文案 = 改文本；配合第 2 项可以按文件版本跑评测；便于 diff 与回滚。
（是否顺带声明插件 `Config` 由你定：文件方案不依赖 schemastery，跨 profile 更稳。）

### 4.2 写作规范（让每条都能被验证）

- **一条规则 = 一个可观察行为**：有触发条件（"当…"）、有动作（"给出 3 个方向"）、有禁区（"不要改无关文件"）。
- **每档 ≤ 8 条**：超过以后模型会丢规则，且每条都在抢注意力。
- **用正例而非形容词**："改动最小的那个文件"比"谨慎"可执行。
- **不许互相打架**：例如"多给想法"和"不要发散"同时出现，模型会随机服从一条。
- **算 token 账**：每个档位的段落长度记进 README；一条规则如果测不出效果就删掉。

### 4.3 提示词 linter（低成本，收益直接）

一个脚本检查：条数、字符/token 长度、否定词密度、祈使句开头、同一档位内是否出现相反指令、
是否缺少"触发条件"、以及和上一版的 diff 摘要。CI 或本地 `node prompts/lint.mjs` 即可。

### 4.4 反馈闭环（用现成信号）

`message-feedback` 已经把评分/分类/备注写进会话日志：

1. 导出近 N 天"差评 + 分类 + 备注"的 assistant 消息，连同当时的档位、任务类型；
2. 按分类聚类，得到"失败模式"（越界改动、太啰嗦、没给选项、忽略约束…）；
3. 每个失败模式对应一条规则的新增/改写，作为候选补丁。

这一步只做**证据收集**，不自动改提示词。

### 4.5 自我迭代（谨慎版）

要做到"自我迭代"，建议是**候选生成 + 离线评测 + 人工采纳**，而不是线上自动改：

1. 给一个"批评者"任务：输入当前提示词 + 20 条失败样例，输出 3 个候选改写（只改相关段落，附理由）；
2. 用第 2 项的平台在**留出任务集**上跑候选，和基线比较；
3. 只有指标不退化才进入人工 review；人工采纳后写入 `prompts/` 并打版本号；
4. 保留上一版，随时可回滚；提示词长度设上限（例如每档 400 token），防止越改越长。

不建议全自动的原因：提示词改动成本极低、验证成本极高，自动迭代很容易漂向"更长、更啰嗦、更保守"，
而且会过拟合到评测集。

### 4.6 版本与记录

`prompts/CHANGELOG.md`：版本号、改了什么、为什么、在哪个评测集上多少分。
第 2 项的结果报告必须引用提示词版本，否则结论不可复现。

## 建议顺序

1. **4.1 提示词外置**（解锁后面所有实验，改动最小）
2. **2 测试平台 Phase 0 → Phase 1**（有了尺子再谈优化）
3. **3 Ultra**（独立性最强，可随时插入，但结论要靠 2 来验证）
4. **4.3 linter + 4.4 反馈闭环**（低成本、持续收益）
5. **1 多采样**（成本最高，等 2 能衡量收益后再做）
6. **4.5 自我迭代**（需要 2 + 4.4 都稳定后才值得尝试）
