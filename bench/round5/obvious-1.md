# 10 行图片转 webp 脚本，要不要拆成 3 个模块？

## 结论：不拆

这不是"为了可维护性牺牲优雅"的权衡，而是没有权衡：拆开是用 3 个文件、2 处 `source`、1 套相对路径约定，换 0 个可维护性收益。

## 为什么"可维护性"在这里是个假理由

维护成本大致 = 阅读成本 × 修改频率 × 耦合面。

- **阅读成本**：10 行看一眼就完，拆开后改一次要在 3 个文件间跳。
- **耦合面**：单一职责脚本只有一个变化轴——命令行参数和 ImageMagick/cwebp 的调用方式。模块化只在"多人 / 多调用方 / 多变化轴"时回本，这里三个都没有。
- **shell 没有模块系统**：`source` 依赖执行目录、变量全局污染、`set -e` 的作用域，都是拆分**新引入**的故障点，不是拆分**消除**的旧故障点。用 3 个文件买到的抽象，比它带来的路径 bug 便宜不了。

一句话：模块化的收益来自边界数量，而这里只有一个边界——"脚本 vs 外部世界"。

## 更值得做的方向（互斥，按成本排序）

1. **不动结构，只加护栏**（推荐，改动最小）
   `set -euo pipefail`、`find -print0 | while read -d ''`、全部加引号、跳过已存在文件、失败计数并以非零码退出。约 5 行，收益远大于拆分。
2. **文件内分节，不拆文件**
   `convert_one()` / `main()` 两个函数，仍是一个文件。成本 0，可读性小涨，风险为零。这是"想整理一下"时唯一值得做的动作。
3. **把可配置项外置，而不是把代码外置**
   顶部集中 `SRC_DIR`、`QUALITY`、`JOBS`，配一个说明头注释。成本 0。
4. **删掉脚本**
   如果这只是"一次性把某个目录转掉"，`mogrify -format webp *.jpg`（或一个 make 目标）就够。成本为负——少维护一个文件。仅在确实一次性时成立，别拿它当长期方案。

## 什么时候该拆（先写下来，触发再看）

- 出现第二个调用方：CI、pre-commit、别的脚本 `source` 它；
- 涨到 ~80–100 行，或出现第二个独立变化轴（缩略图、上传、EXIF 处理）；
- 某个纯函数需要被单元测试；
- 有第二个人经常改。

在这之前，拆分的唯一产出是三个更小的、彼此不知道对方存在的文件。

## 如果将来真的要拆

两层就够：`lib.sh`（纯函数，可测）+ 入口（参数解析、CLI、退出码）。

**不要按"读取 / 转换 / 写出"切成三个模块**——那是数据流的三个阶段，不是模块边界；按它切完，每个模块都只有一个调用方，等于把顺序代码换成了三份样板，还多出两条接口要维护。真正稳定的边界通常是"纯逻辑 vs 副作用"。
